# Décisions d'architecture — Orthros

Chaque décision est numérotée, datée, et donne le pourquoi. Une décision révisée n'est pas effacée : on ajoute une entrée qui la remplace.

## D001 — 2026-09-18 — Langage : JavaScript ES modules + JSDoc, sans étape de build
Le navigateur charge `src/` tel quel et Node exécute les mêmes fichiers pour les tests. Pas de TypeScript/bundler : itération instantanée, zéro dépendance runtime. Le typage est apporté par JSDoc (vérifiable plus tard avec `tsc --checkJs` si utile). Les parties critiques en perf ne sont pas l'interpréteur (référence) mais le code WASM généré par le JIT.

## D002 — 2026-09-18 — Mémoire invité : identité totale sur une `WebAssembly.Memory` de 2 Go
Adresse invité = offset mémoire. Vérifié dans Node : allouer 2 Go (partagé ou non) prend 5 ms et ne coûte rien en RSS tant que les pages ne sont pas touchées. Conséquences : le JIT émet des `i32.load/store` directs (aucune traduction d'adresse), `VirtualAlloc` n'est que de la comptabilité, pas de détection de faute de page en v1 (une lecture d'une page non mappée renvoie 0). Région privée de l'émulateur : `0x7FF00000–0x7FFFFFFF` (états CPU des threads, TEB/PEB, données internes) ; thunks d'import : `0x7FE00000–0x7FEFFFFF`.

## D003 — 2026-09-18 — Threads invités : green threads sur un seul worker
Tous les threads Win32 du jeu s'exécutent sur un seul thread JS (un Web Worker), commutés (a) à chaque appel API bloquant, (b) par préemption à intervalle de temps aux frontières de blocs, uniquement au niveau de dispatch le plus externe. Raison : l'état Win32 reste mono-thread (pas de verrous ni RPC), WebGL est appelable depuis n'importe quel thread invité, et un jeu de 2004 a une boucle principale mono-thread. Limite connue : un thread bloqué dans un callback imbriqué qui attend un autre thread lui-même bloqué au-dessus de lui sur la pile JS ne peut pas être réveillé par timeout (faux deadlock rare). Plan B si ça bloque : un worker par thread invité + RPC vers un worker « noyau ».

## D004 — 2026-09-18 — Frontière API : le code JIT ne rappelle jamais JS de façon imbriquée
À chaque appel d'import Win32 (ou événement de sortie), le code WASM flush les registres dans la structure d'état du thread et **retourne** au dispatcher JS avec un code de sortie. La pile WASM est donc toujours vide à une frontière API : commutation de thread = changement de pointeur d'état ; callbacks (WndProc, thread start, qsort…) = boucle de dispatch imbriquée jusqu'au retour à une adresse trampoline. Coût : un aller-retour WASM→JS par appel API (~100 ns), négligeable.

## D005 — 2026-09-18 — JIT : modules WASM par région, table funcref partagée, drapeaux paresseux
Une région (fonction ou ensemble de blocs) = un module WASM généré à la volée ; registres dans des locals à l'intérieur d'une région, sauts intra-région par `br_table`, sauts inter-région par cache EIP→index dans une `WebAssembly.Table` partagée + `call_indirect`/`return_call_indirect`. Drapeaux calculés paresseusement (dernier résultat + opérandes). x87 émulé en f64 (précision 80 bits non reproduite : compromis classique acceptable pour un jeu). MMX stocké à part des registres x87 (pas d'aliasing exact).

## D006 — 2026-09-18 — Oracle de conformité CPU : le processeur natif du serveur
Le serveur est un x86-64 Linux capable d'exécuter des ELF 32 bits. Le « modèle de référence écrit à part » est donc un harnais natif 32 bits (C freestanding, syscalls directs) qui exécute les mêmes séquences d'instructions générées aléatoirement et renvoie registres/drapeaux/mémoire. Aucun second interpréteur à maintenir, et la vérité vient du silicium. Les drapeaux non définis par l'ISA sont masqués.

## D007 — 2026-09-18 — VFS : lecture synchrone par XHR range + cache dans le worker
`ReadFile` est synchrone côté invité. Dans le worker, XHR synchrone avec `Range` par blocs (1 Mo) + cache LRU + lecture anticipée, puis miroir OPFS (`createSyncAccessHandle`) pour les rechargements. Alternative écartée pour l'instant : dispatcher async/JSPI (contagieux, plus lent à mettre au point).

## D008 — 2026-09-18 — Exécution dans un Web Worker + OffscreenCanvas
Le cœur tourne dans un worker (WebGL2 via OffscreenCanvas, `Atomics.wait` pour dormir précisément). Le thread principal ne fait que HUD, transfert des entrées, et l'AudioWorklet alimenté par un ring buffer en SharedArrayBuffer.

## D009 — 2026-09-18 — Overrides de DLL génériques via manifest
Le dossier de la cible contient un `dsound.dll` tiers (wrapper) ; l'ordre de recherche Windows le chargerait avant l'implémentation intégrée. Mécanisme générique : `manifest.json` → `dllOverrides: { "dsound": "builtin" | "native" }`. C'est un flag de compat universel, pas du code spécifique au jeu.

## D011 — 2026-09-18 — Politique d'exactitude x87 en f64
Ce qui est exact : PC=53 en arrondi au plus près (le résultat f64 est le même que le 80 bits arrondi à 53), PC=24 dans tous les modes d'arrondi (via termes d'erreur exacts TwoSum/TwoProduct), conversions entières, FPREM/FPREM1 (écart d'exposant < 64), comparaisons, réponses masquées. Ce qui ne l'est pas : PC=64 (mantisse 64 bits impossible en f64), arrondi dirigé en PC=53, transcendantales (Math.* ≈ 1e-13 relatif), payload des NaN. Justification : un jeu MSVC de 2004 tourne en PC=53 (CRT) ou PC=24 (Direct3D sans FPU_PRESERVE) et en arrondi au plus près sauf autour de `_ftol` (FISTP avec RC=trunc, exact chez nous). Les cas non exacts sont couverts par une tolérance dans les tests de conformité, pas ignorés.

## D012 — 2026-09-18 — Générateur de conformité : llvm-mc + snippets aléatoires + drapeaux indéfinis masqués
Les cas sont assemblés par llvm-mc (encodages sûrs), les branches sont encodées à la main pour rester dans le snippet, et chaque cas porte un masque des drapeaux définis par l'ISA (les drapeaux « undefined » du SDM ne sont pas comparés). Les fautes natives (#DE…) sont comparées sur l'EIP fautif et l'état au moment de la faute, en ignorant la mémoire sous ESP (le noyau y écrit le signal frame).

## D013 — 2026-09-18 — Structure du JIT x86→WASM
Une région = un ensemble de blocs de base atteignables par branchements directs depuis un point d'entrée (≤ 48 blocs / 400 instructions), traduite en **une fonction WASM** `(bloc, état) → EIP suivant | 0`. Les 8 registres, EFLAGS, l'état de drapeaux paresseux (kind, res, a, b), FS base et TOP x87 vivent dans des locals pour toute la région ; un `loop` + `br_table` dispatch les blocs, les sauts intra-région ne touchent pas la mémoire. Les sorties (saut inter-région, thunk d'import, faute, tranche de temps, SMC) réécrivent l'état dans le bloc d'état du thread. Un **dispatcher WASM** (module runtime) enchaîne les régions via une table de hachage EIP→(fonction, bloc) en mémoire invité et une `WebAssembly.Table` partagée ; un raté renvoie à JS qui traduit la région manquante. Les instructions sans traduction native passent par un import `fallback(eip)` qui exécute **une** instruction dans l'interpréteur de référence (registres flushés/rechargés autour) : le JIT est donc complet par construction et s'optimise instruction par instruction. Drapeaux paresseux : producteur connu statiquement dans le bloc → conditions inlinées ; sinon appel au helper WASM `flags()`. Précision x87 24 bits via `round24` (arrondi de mantisse exact à plage étendue). Détection de code auto-modifiant : test d'un bitmap de pages à chaque store non-pile (sortie SMC → invalidation des régions de la page). Mesure (bench.exe, entier + x87) : 65,8× l'interpréteur, ~0,8 G instructions/s sur le serveur.

## D014 — 2026-09-18 — Le JIT n'émule pas les fautes de pile x87
Les accès à un registre x87 vide (dépassement/sous-dépassement de pile) produisent des NaN indéfinis sur le matériel ; aucun programme valide ne s'y fie. Le JIT ne teste pas les tags (qu'il maintient quand même, pour l'interpréteur de repli). Les cas de conformité qui déclenchent une faute de pile (bit SF du FSW dans le résultat de l'oracle) sont exclus pour le JIT, pas pour l'interpréteur.

## D010 — 2026-09-18 — Outillage
Node 24 (tests `node --test`, serveur), Playwright + Chromium headless (harnais), clang-18/lld-18 (oracle natif, PE de test compilés sans CRT), python3 (générateurs de tests). Le serveur n'a pas de GPU exploitable (Matrox G200) : le headless valide la correction (SwiftShader), la perf se mesure sur un vrai client.

## D015 — 2026-09-18 — Chemins rapides d'API en WASM (FAST_TABLE)
Le jeu appelle certaines API triviales des millions de fois (`timeGetTime`, `GetTickCount`, `InterlockedIncrement`…) : à ~1 µs le passage par JS, la calibration CPU du jeu (~20 M d'appels) coûtait des minutes. Le dispatcher WASM consulte une table d'un octet par thunk : les API marquées « rapides » sont exécutées en WASM (lecture de KUSER_SHARED, arithmétique) sans sortir vers JS ; le reste garde la sortie THUNK (D004). Le marquage est fait par l'`ApiRegistry` (hook `onThunk`), donc générique. Les appels rapides ne comptent pas dans `apiCalls` ni dans la trace des derniers appels.

## D016 — 2026-09-18 — SEH par continuation
Un handler MSVC (`_except_handler3`, `__CxxFrameHandler`) peut ne jamais revenir (goto non local vers `__except` après `RtlUnwind`). Le dispatch n'est donc pas une boucle JS qui appelle chaque handler : le handler est *entré* avec une adresse de retour vers un thunk interne (`__seh_return`) dont le côté JS lit la disposition et continue (frame suivant, ou reprise depuis le CONTEXT). `RtlUnwind` appelle les handlers en mode déroulement via `callGuest` (ils reviennent toujours), place son CONTEXT et ses frames **sous l'ESP courant** (les locals du handler C++ appelant sont vivants), fixe FS:[0] à la frame cible et revient normalement avec EAX = valeur de retour — équivalent au `ZwContinue` de NT sur x86 (TargetIp = adresse de retour). Un saut vers l'adresse 0 est une violation d'accès (pas une sortie « code 0 »).

## D017 — 2026-09-18 — CRT intégrée et DLL natives chargées telles quelles
`msvcr71.dll`/`msvcp71.dll`/`mfc71.dll` du dossier du jeu sont chargées **natives** (elles sont dans le dossier, l'ordre de recherche Windows les préfère) : leur code x86 tourne dans le JIT comme le jeu. L'implémentation intégrée `msvcrt.dll` (cdecl, `_except_handler3`, `_CxxThrowException`, qsort par rappel invité, math via `retDouble`) sert aux binaires qui importent la CRT système (dbghelp, PE de test). Pas de réécriture de la CRT du jeu.

## D018 — 2026-09-18 — Sémantique des jokers Win32 dans FindFirstFile
`*.` doit lister les noms sans extension (le jeu énumère ainsi ses sous-dossiers d'archives), `*.*` tout, `abc.*` aussi `abc`, `?` ne franchit pas un point. Implémentation de la sémantique `FsRtlIsNameInExpression` avec les jetons DOS (`DOS_STAR`, `DOS_QM`, `DOS_DOT`) que `FindFirstFile` produit, au lieu d'une simple regex glob.

## D019 — 2026-09-18 — GDI+ : images = surfaces 32 bits ARGB en mémoire invité
Le format mémoire de `PixelFormat32bppARGB` est celui de nos surfaces GDI (B,G,R,A) : `LockBits` en 32 bits rend directement le tampon de l'image (pas de copie), les autres formats passent par une conversion dans un tampon du heap. Les images créées sur un `scan0` de l'appelant restent liées à ce tampon (relecture avant lecture, réécriture après écriture). Décodeurs JPEG (base + progressif, suréchantillonnage « fancy » identique à libjpeg, YCbCr en virgule fixe) et PNG (tous types, Adam7) écrits de zéro et validés contre PIL (tolérance 3/255 pour le JPEG : IDCT entière ≠ flottante).

## D020 — 2026-09-18 — COM : vtables de thunks, objets en mémoire invité, méthodes JS
Une interface COM = une vtable allouée une fois dans le heap invité dont chaque entrée est un thunk d'API (`com.dll!Interface::Method`, argc = 1 + arguments) ; un objet = un bloc invité `[vtable, marqueur, id]` associé à une implémentation JS. `QueryInterface`/`AddRef`/`Release` sont génériques (chaîne d'héritage + `iids` supplémentaires déclarés par l'implémentation), les méthodes absentes sont tracées une fois et renvoient `E_NOTIMPL`. DirectInput, DirectSound et Direct3D 8 sont bâtis dessus ; `CoCreateInstance` résout les CLSID enregistrés (DirectSound). L'ordre des méthodes vient des en-têtes publics du SDK.

## D021 — 2026-09-18 — Attentes bloquantes déroulées (parking) au niveau supérieur
Le modèle « threads verts imbriqués » (D003) affamait le thread principal : un thread ouvrier bouclant sur `Sleep(1)` gardait la pile JS et le principal, pourtant prêt, ne tournait qu'une tranche par seconde. Désormais tous les threads s'exécutent en tranches depuis une boucle d'ordonnancement de niveau 1. Un appel d'API bloquant au niveau 1 (`Sleep`, `WaitFor*`, `EnterCriticalSection`, `GetMessage`…) **se déroule** : le handler lève `WaitUnwind`, l'appel est annulé (EIP/ESP remis à l'entrée du thunk), le thread est garé avec sa condition de réveil ; réveillé, il ré-exécute l'appel et `block()` lui rend le résultat enregistré. Les handlers ayant des effets de bord avant l'attente (`SignalObjectAndWait`, `SuspendThread`) consultent `thread.resuming`. Le blocage à l'intérieur d'un rappel (WndProc, DllMain) ne peut pas dérouler les frames JS de l'hôte : il exécute les autres threads imbriqués comme avant.

## D022 — 2026-09-18 — Regroupement des régions JIT en modules multi-fonctions
Un module WASM par région (D013) coûte ~50 Ko de métadonnées V8 par instance (feedback vectors, tables, func refs…) : le chargement du jeu traduit ~20 000 régions en une minute et le tas JS explosait (4 Go). Chaque région est d'abord compilée seule (exécution immédiate), puis toutes les 128 régions les corps de fonction conservés sont ré-émis dans **un** module de 128 fonctions dont les exports remplacent les entrées de la table funcref ; les instances individuelles deviennent collectables. Coût : une seconde compilation par région (Liftoff, quelques dizaines de ms par lot), re-tiering TurboFan des fonctions chaudes.

## D023 — 2026-09-18 — Table de hachage EIP du JIT : 2^20 entrées, réinsertion au lieu de retraduction
La table EIP→(fonction, bloc) de 64 K entrées était pleine dès ~3 300 régions (≈20 blocs chacune) : chaque éviction faisait retraduire le bloc à sa prochaine exécution, d'où une tempête de traductions (20 000 régions en quelques secondes) et l'explosion mémoire. La table occupe désormais 16 Mo (2^20 entrées) juste sous les thunks (l'espace utilisateur s'arrête à `JIT_HASH_BASE`), et une carte des blocs vivants permet de **réinsérer** une entrée évincée sans retraduire.

## D024 — 2026-09-18 — Orientation Direct3D → WebGL : pas de retournement à l'écran, textures cibles retournées
Direct3D et OpenGL partagent l'orientation de l'espace de clip (y vers le haut) : le rendu vers le tampon arrière ne retourne rien (les rectangles de viewport/scissor sont convertis en origine bas-gauche). Seules les cibles de rendu texturées diffèrent : une surface D3D a sa ligne 0 en haut, une texture GL sa ligne 0 « en bas » ; on rend donc dans les FBO avec `u_flipY = -1` (uniform, pas de variante de programme), rectangles non convertis et faces de culling inversées, ce qui donne aux textures de rendu l'ordre de lignes D3D pour leur échantillonnage ultérieur et les relectures (`GetRenderTargetData`). Le premier rendu du menu, retourné verticalement, a mis en évidence l'erreur du retournement global initial.

Sens des faces : une face avant Direct3D est **horaire telle qu'on la voit à l'écran** ; l'espace de clip étant partagé, l'espace fenêtre GL garde cette orientation visuelle (`frontFace(CW)` à l'écran, `CCW` sur les cibles retournées), puis `D3DCULL_CCW` = éliminer les faces arrière GL et `D3DCULL_CW` les faces avant ; le stencil bifacial suit la même convention. La première version raisonnait en coordonnées écran « y vers le bas » (horaire mathématique ≠ horaire visuel) et éliminait les étiquettes des boutons du menu (quads tracés avec `D3DCULL_CW`). Le PE de test `dx9.exe` trace désormais un triangle horaire (visible) et un anti-horaire (éliminé) sous `D3DCULL_CCW`.

## D025 — 2026-09-18 — Images complètes uniquement : tampon arrière en FBO, trames explicites vers la page
Deux sources de scintillement en Chromium headless : (1) le rendu Direct3D allait directement dans le framebuffer par défaut du canvas, que le navigateur compose dès que le worker rend la main — au milieu d'une image, quand le jeu attend (ordonnanceur D021), on voyait des images à moitié tracées ; (2) un `OffscreenCanvas` transféré depuis la page (`transferControlToOffscreen`) est composé automatiquement en fin de tâche et, sous charge, la couche apparaissait vide (noir) sur ~40 % des captures — reproduit avec une page minimale et un worker occupé. Désormais **chaque cible de rendu est un FBO**, y compris les tampons arrière (le framebuffer par défaut ne reçoit qu'un `blitFramebuffer` complet dans `Present`), et le worker possède ses canvas (`new OffscreenCanvas`) dont il envoie les trames complètes à la page par `transferToImageBitmap` → `ImageBitmapRenderingContext` (couches GL et GDI). La couche GDI conserve l'image du bureau côté worker (`transferToImageBitmap` vide le canvas). Effet de bord utile : un device plein écran possède le mode d'affichage (`WindowManager.setDisplayMode`, partagé avec `ChangeDisplaySettings`) et place sa fenêtre en (0,0) comme le runtime D3D, ce qui met les coordonnées souris (messages en coordonnées client) en accord avec l'image.

## D026 — 2026-09-18 — DirectSound : curseurs pilotés par l'horloge, position de mixage suiveuse
Le curseur de lecture d'un tampon DirectSound avançait au rythme de ce que l'hôte consommait (anneau de l'AudioWorklet). En headless (sortie audio factice, cadence irrégulière) ou quand le contexte audio est suspendu (politique d'autoplay), le curseur traînait : la bibliothèque audio du jeu (Miles) voyait un tampon qui n'avance pas, le recréait en boucle (create/lock/play toutes les quelques ms) et le son restait muet — aggravé par le tampon primaire sans stockage mixé comme un tampon de taille 0 (NaN dans la sortie). Désormais les curseurs avancent avec l'horloge de la VM (temps réel, comme un périphérique matériel), le mixeur garde par tampon une **position de mixage** qui avance avec les trames rendues et se resynchronise sur le curseur quand elle dérive (> 250 ms, sortie suspendue, `SetCurrentPosition`), et le tampon primaire n'est jamais mixé (il *est* le mixage). Le jeu diffuse alors normalement (pics ~0,1 sur la musique du menu) ; le test `dx.exe` conserve ses vérifications de curseurs sous horloge virtuelle.

Entrées clavier : le caractère fourni par le navigateur (`e.key`, dépendant de la disposition) est attaché à l'appui de touche et n'est émis qu'en `WM_CHAR` par `TranslateMessage`, comme Windows ; l'ancienne double émission (message `WM_CHAR` direct + traduction) dupliquait le texte saisi (« Orthros » + « orthros » dans le nom de profil).

## D027 — 2026-09-19 — SSE/SSE2/SSE3/MMX traduits en WebAssembly SIMD (fin des replis interpréteur vectoriels)
Le JIT ne traduisait aucune instruction vectorielle : chaque MOVAPS/MULPS/ADDPS/SHUFPS/MOVQ… sortait du WASM, décodait dans l'interpréteur JS et revenait (~470 ns) — dès que la bibliothèque audio du jeu décodait sa musique, ~2 millions de replis par seconde occupaient tout le worker (menu 40 → 20 fps, écran d'escarmouche 3 fps, tranches de 12 ms durant 160 ms). Désormais deux modules d'extension (`translate-sse-float.js`, `translate-sse-int.js`, sur le modèle de `translate-x87.js`, helpers dans `translate-sse-common.js`) traduisent les 189 mnémoniques SSE/SSE2/SSE3/MMX du décodeur (sauf FXSAVE/FXRSTOR, laissés au repli) avec les instructions `v128` de WebAssembly, encodées dans `wasm.js` (préfixe 0xFD, table vérifiée par `tests/wasm-simd.test.js`).
Choix : registres XMM/MM/MXCSR **résidents en mémoire** dans le bloc d'état (lus/écrits par chaque instruction : cohérence gratuite avec les replis, les changements de thread et le consolidateur ; trois locaux `v128` de travail seulement) ; sémantique x86 reproduite bit à bit contre l'oracle natif : MINPS/MAXPS = `pmin/pmax` à opérandes inversés (second opérande retourné sur NaN/égalité), décalages avec compte ≥ largeur → 0 ou remplissage de signe (WASM prend le compte modulo la largeur), conversions flottant→entier avec « indéfini » 0x80000000 sur NaN/débordement et arrondi MXCSR (RC) sélectionné à l'exécution par `br_table`, formes scalaires qui préservent les voies hautes, MOVSS/MOVSD/MOVQ qui étendent par zéro depuis la mémoire mais fusionnent registre à registre, tout accès MM qui force TOP=0 et tags=0xFF (comme l'interpréteur, D005), COMISS/UCOMISS via `materialize()` puis écriture directe d'EFLAGS ; un magasin 16 octets non aligné qui chevauche deux pages fait un second test SMC (`smcCheckEnd`) et l'hôte invalide 16 octets à partir de l'adresse fautive.
Écarts assumés (mesurés par la suite `verify_float_known`, 400 cas) : DAZ/FTZ ignorés par le JIT (WASM n'a pas de flush-to-zero ; 20/51 cas arithmétiques dénormaux diffèrent du matériel — un garde `if (MXCSR & 0x8040) repli` coûterait +15 % sur la phase SSE du bench, refusé tant qu'aucun jeu n'en dépend), arrondi RC ≠ « au plus près » non honoré sur l'arithmétique et les conversions entier→flottant dans les deux exécuteurs (59/112 et 47/110 cas — identique à avant), pièges mémoire dans un magasin vectoriel natif imprécis (EIP de la région, comme tout accès natif). Au passage l'interpréteur a été corrigé sur trois points relevés par les vérificateurs contre l'oracle : EMMS remet TOP à 0, MIN/MAX ne subissent pas FTZ (ils renvoient un opérande tel quel), et la règle x86 de propagation des NaN (premier opérande NaN silencié, sinon second, sinon « indéfini réel » négatif ; ops unaires depuis la source seule) remplace la canonisation JS — 85/85 cas de charge utile NaN passent maintenant.
Validation : suites oracle `sse` (1500 cas, étendue : PSHUFW, PSxxDQ, MOVQ/MOVNT*, conversions MMX↔XMM, LD/STMXCSR, SSE3, décalages 64 bits, ±2^31…), `verify_float`, `verify_int`, `verify_mech` (≈4500 cas ; flags paresseux, blocs, SMC, FS/GS/a16, x87↔MMX) vertes sur les deux exécuteurs ; `tests/jit-sse-mechanics.test.js`. Mesures : bench phase SSE interpréteur 2 989 ms → JIT 16 ms (avant : 3 018 ms via replis, 1,0×), somme de contrôle inchangée ; jeu, menu avec audio : 20 → 39,5 fps, replis 1,8 M/s → 2 k/s (PUSH/POP de segment, transcendantes x87).

## D028 — 2026-09-19 — Rappels de fenêtre au niveau invité (trampoline) : plus de frame JS entre l'appelant et la WndProc
Le détecteur de blocage ajouté au harnais headless (le worker cesse d'émettre ses statistiques → pause du thread par CDP et pile d'appels) a montré le cas limite de D021 : la WndProc du jeu, invoquée par `DispatchMessage` depuis JS (`callGuest`, exécution imbriquée), appelait `WaitForSingleObject` ; l'attente ne pouvant se dérouler (frame JS en dessous), l'ordonnanceur exécutait les autres threads *par-dessus*, qui bloquaient à leur tour (Sleep/Wait imbriqués sur quatre niveaux) jusqu'à ce que la condition du plus profond dépende d'un thread coincé plus bas dans la pile JS : interblocage, worker figé (menu figé au clic sur SKIRMISH). Désormais `DispatchMessage`, `SendMessage` (vers une procédure invitée) et `CallWindowProc` ne rappellent plus la WndProc depuis JS : le handler pousse les arguments et l'adresse du thunk `__callback_return` sur la pile invitée, saute dans la procédure et rend la main au dispatcher (`Vm.tailCallGuest`, sentinelle `TAIL_CALL`) ; au retour, le thunk restaure EIP/ESP depuis une continuation enregistrée par thread (pile LIFO, entrées abandonnées par un saut non local ignorées) et exécute la suite éventuelle en JS (`WM_PAINT` → présentation). La pile JS reste plate, donc une attente dans la WndProc se gare comme n'importe quelle attente de niveau supérieur (D021). Les rappels émis par la logique interne du gestionnaire de fenêtres (WM_SIZE/WM_CREATE pendant `SetWindowPos`/`CreateWindow`, DllMain, TLS) restent imbriqués : courts en pratique, à convertir s'ils bloquent un jour.

## D029 — 2026-09-20 — Chaînage des régions JIT par appels terminaux, registres passés en paramètres
Chaque transition entre régions (saut/appel/retour hors de la région courante, plusieurs millions par seconde en jeu) revenait au dispatcher WASM après avoir écrit les 15 locaux (GPR, EFLAGS, drapeaux paresseux, FS, TOP) dans le bloc d'état, puis la région suivante les relisait ; le dispatcher seul pesait 10 % du temps du worker. Désormais la signature d'une région est `(bloc, état, eax…edi, eflags, lzop, lzres, lza, lzb, fs) → i32` — les seize premiers locaux sont des paramètres, les émetteurs sont inchangés — et la sortie « saut » tente d'abord de **chaîner** : si la cible n'est ni un thunk, ni `ST.STOP_AT`, que le budget `ICOUNT` reste positif et que la table de hachage la connaît, la région fait un `return_call_indirect` (appels terminaux WebAssembly, validés au démarrage, repli sur l'ancien chemin sinon) vers la fonction trouvée en lui passant les locaux tels quels (drapeaux paresseux compris) ; sinon elle rend la main au dispatcher comme avant (traduction, thunk, tranche). Le dispatcher charge lui-même les 14 arguments depuis le bloc d'état. Les vérificateurs ont ajouté deux corrections : le budget est désormais aussi débité aux sorties inter-régions (une boucle faite uniquement de sauts inter-régions ne rendait jamais sa tranche), et l'EIP est écrit avant le chaînage pour que les pièges dans une région chaînée soient rapportés à la bonne région. Mesures : micro-bench de transitions 19 → 11 ns ; en jeu, dispatcher 10,1 % → 1,8 % du worker, p99 38 → 33 ms, fps moyen inchangé (35) — le worker reste saturé par l'hôte graphique et les appels d'API (profil désormais plat).

## D030 — 2026-09-20 — Pile x87 en locaux WebAssembly dans les régions x87 (décalage statique, mot d'étiquettes logique)
Le profil en jeu plaçait 50 % du temps du worker dans des régions dominées par le x87 (FLD 15 %, FMUL 10 %, FSTP 9 %, FADDP/FADD/FSUB/FXCH ≈ 15 %) : chaque instruction relisait et réécrivait ST(i) dans le bloc d'état (`FPR[(TOP+i)&7]`, mot d'étiquettes chargé/stocké à chaque push/pop) et la précision 24 bits passait par l'import `round24`. Désormais une région contenant une instruction x87/MMX (mnémonique `F*`, EMMS, tout opérande MM) est une **région x87** : à l'entrée elle charge ST(0..7) dans huit locaux f64 (`L_ST0..`), le mot d'étiquettes abrégé dans `L_FTW` et les bits PC/RC du mot de contrôle dans `L_FPC` ; elle les réécrit à chaque sortie (chaînage compris), aux codes de sortie et autour de chaque repli interpréteur (qui travaille sur la copie mémoire ; FXAM, FNSTENV, transcendantes et m80 restent des replis). Les autres régions sont émises octet pour octet comme avant. À l'intérieur d'un bloc, push/pop/FINCSTP/FDECSTP ne déplacent aucun local : ils changent un **décalage statique** (`stShift`, ST(i) = local `(i+shift)&7`, TOP réel = `L_TOP+shift`) matérialisé une seule fois là où le bloc est quitté (sortie, branchement, repli, remise à zéro de TOP par MMX/EMMS/FNINIT — rotation à l'exécution si TOP ≠ 0) ; un bloc équilibré (`fld … fstp`) ne fait aucun mouvement. `L_FTW` est tenu en ordre logique (bit i = ST(i) valide, rotation par TOP au chargement/à l'écriture) : chaque mise à jour d'étiquette est un masque constant, et les étiquettes déjà posées par un store du même bloc ne sont pas reposées. Précision 24 bits : `f32.demote`/`f64.promote` en ligne quand RC = au plus près et la valeur est dans la plage normale du float (bit à bit identique à `round24`), `round24` sinon (plage d'exposant étendue, arrondis dirigés : sémantique inchangée). Les fautes de pile restent non émulées (D014). Mesures : bench.exe phase fpu 270 → 70 ms (somme de contrôle identique), micro-bench x87 (`tools/x87-bench.mjs`) boucle produit scalaire 24,0 → 18,1 ns/itération, PC = 24 bits 33,9 → 26,5 ns ; coût d'entrée/sortie d'une région x87 ≈ +3,5 ns par transition chaînée (boucle coupée en deux régions 34 → 41 ns/itération). Limite : comme pour les registres généraux, un piège WASM dans une région x87 laisse dans le bloc d'état la pile x87 telle qu'à l'entrée de la région.

## D031 — 2026-09-20 — Attentes actives `Sleep(0)` : bornées à la résolution des timers Windows
Les statistiques par thread montrent le thread principal du jeu appelant `Sleep(0)` + `timeGetTime` ~100 000 fois par seconde entre deux images (limiteur de cadence). Sous Windows, `Sleep(0)` rend la main aux threads prêts et revient aussitôt s'il n'y en a pas : sur une machine multicœur cela brûle un cœur sans gêner le jeu. Dans Orthros, tout tourne sur un seul worker : chaque itération coûte un aller-retour WASM→JS→WASM (~10 µs) et le worker paraît saturé alors que le jeu attend. Règle générique : après 32 `Sleep(0)` consécutifs (moins de 50 µs entre deux, aucun autre appel d'API entre-temps) et si aucun autre thread n'est prêt, la tranche dort 1 ms — ce que donne de toute façon `Sleep(1)` avec `timeBeginPeriod(1)` sous Windows. Pas d'effet mesurable sur le jeu (12 déclenchements en 5 min : un autre thread est presque toujours prêt), mais la mesure a établi que ~38 fps en jeu est le rythme choisi par le jeu, pas une limite CPU d'Orthros ; la charge réelle du worker se lit dans le profil hors `dispatchThunk`/`runThread`/`now` (≈14 % de tourniquet).

## D032 — 2026-09-20 — Attentes satisfaites à l'instant du signal (transfert au dormeur, jamais à un tiers)
Constat (traces `apisite`, détail High) : à la transition entre deux scènes du menu 3D, le thread principal crée un mutex A libre et un mutex B qu'il possède, lance un thread d'écran de chargement qui prend A pour toute sa durée de vie et sonde B (`WaitForSingleObject(B, 0)` → `WAIT_TIMEOUT` = « continue »), puis attend que A soit tenu : `WaitForSingleObject(A, 1)` en boucle jusqu'à un `WAIT_TIMEOUT`. Sous Orthros, le thread principal ré-acquérait A à 1,2 M itérations/s sans jamais le voir tenu (livelock à 20 fps sur l'écran de chargement). Cause : l'ordonnanceur (D021) réveillait un thread garé en notant « condition vraie » et le thread *consommait* l'objet à la ré-exécution de l'appel — entre les deux, le thread libérateur pouvait reprendre l'objet (famine) ou le dormeur le prendre alors qu'un autre l'avait déjà (vol : deux propriétaires). Le noyau Windows satisfait une attente **au moment du signal** : `ReleaseMutex` transfère la propriété au premier attendant, `SetEvent` auto-reset ne réveille qu'un thread, etc. Règles adoptées : (1) chaque attente garée porte une *revendication* (`claim`) exécutée dès que sa condition est vraie — à `ReleaseMutex`/`LeaveCriticalSection`/`SetEvent`/`ReleaseSemaphore`/sortie de thread (`sched.signal()`) ou au prochain point d'ordonnancement — qui prend l'objet (propriétaire, compteur, remise à zéro de l'événement) et fixe le code de retour ; la ré-exécution de l'appel ne fait que rendre ce résultat. (2) Un appel ré-exécuté après un parking est signalé dans l'état du thread (`ST.RESUMING`) : les chemins rapides d'API en WASM (D015 — `EnterCriticalSection` inline, qui aurait vu « propriétaire = moi » et compté une récursion) s'effacent alors devant le handler JavaScript. Vérification : `tools/pe/sync.c` (transfert de mutex et de section critique sous un libérateur qui ré-acquiert en boucle serrée, un réveil par signal d'événement auto-reset / unité de sémaphore, la poignée de main ci-dessus, abandon) vert sur les deux exécuteurs ; en jeu, la seconde scène du menu 3D se charge et s'affiche. Diagnostics ajoutés : journal `apisite` (premiers appels de chaque site d'appel par thread, avec arguments et résultat), table des objets de synchronisation et anneaux des transferts contestés dans le rapport de fin.

## D033 — 2026-09-23 — Transcendantes x87 en WebAssembly pur (noyaux du module runtime)
Les instructions F2XM1, FSCALE, FYL2X, FYL2XP1, FSIN, FCOS, FSINCOS, FPTAN et FPATAN étaient les seuls replis interpréteur restants dans le code chaud : ~2 M replis/s pendant la suite de benchmarks de première exécution du jeu (F2XM1 + FSCALE de sa fonction exponentielle), 40-60 k/s dans la scène 3D du menu en détail High (FSIN, FPATAN). Un repli coûte ~150-300 ns (sortie de région, interpréteur, rechargement des locaux x87) contre 8-35 ns pour l'instruction native. Choix : des **noyaux mathématiques en WebAssembly pur** définis dans le module runtime (comme `round24`) et importés par les régions — jamais d'appel vers JavaScript depuis le code traduit (D004) ; `Math.*` ne servent que de référence dans les tests. Écrits de zéro à partir des définitions : `exp2m1` (réduction, polynôme ajusté et vérifié en précision arbitraire, `tools/gen_fpmath_exp.py`), `log2`/`log2p1` (décomposition binaire, série de atanh), `scalb` (manipulation d'exposant, un seul arrondi — le matériel n'en fait qu'un dans les dénormalisés, là où l'interpréteur en fait deux), `sin`/`cos`/`tan`/`sincos` (réduction de Cody-Waite en double-double jusqu'à ~1,6·10⁶, réduction de Payne-Hanek au-delà avec une table de bits de 2/π calculée par `tools/gen_pi_bits.py`, polynômes sur |r| ≤ π/4), `atan2` (table atan(k/8) en double-double, `tools/gen_atan_table.py`). Précision mesurée : exp/log ≤ 0,83 ulp contre une référence exacte en BigInt, sin/cos à 0,5 ulp de V8 sur tout le domaine |x| < 2^63 (y compris 10^300), tan ≤ 1,6 ulp, atan2 ≤ 1 ulp — bien en deçà de la tolérance 10⁻¹³ de la suite oracle, et souvent plus précis que le FPU réel lui-même au-delà de |x| ≈ 10⁷ (réduction sur 66 bits du matériel, mesurée sur l'oracle : la suite `verify_trans` ne compare les valeurs trigonométriques que sous cette borne). Sémantique alignée sur l'interprète (C2 et ST inchangé pour |x| ≥ 2^63, IE + indéfini sur NaN, pas d'arrondi PC, C1 non modélisé) pour que les deux exécuteurs restent d'accord ; les écarts de fidélité communs aux deux exécuteurs relevés au passage (±inf en argument trigonométrique → IE + indéfini sur le matériel, QNaN propagé silencieusement, ES levé seulement sur exception non masquée, opérandes invalides de FYL2X/FSCALE) sont consignés dans la suite `verify_trans_known` pour une correction conjointe. Résultat : bench phase `trans` 1 510 → 288 ms (0 repli), zéro repli pendant tout le démarrage du jeu ; la suite de benchmarks du jeu étant bornée en temps, son score monte (+31 %/+47 % de MIPS dans les fenêtres concernées) sans raccourcir la phase.

## D034 — 2026-09-23 — Exceptions x87 : sémantique matérielle (IE/ES, NaN, infinis)
Les écarts communs aux deux exécuteurs consignés en D033 (`verify_trans_known`) ont été mesurés sur l'oracle (`tools/gen/verify_trans_probe.py`, AMD EPYC 7402P) puis corrigés à l'identique dans l'interpréteur (`X87.raise`, `nan1`/`nan2`, `trigSpecial`, `scalb`) et le JIT (`translate-x87.js` : `raise`, `nanOutcome`, `trigArg` ; noyau `nan2` en WebAssembly pur, `fpmath-nan.js`). Règles adoptées : (1) une exception **masquée** ne lève que son drapeau, ES n'est levé que si elle est démasquée dans le mot de contrôle (SDM 8.1.3 ; aucune faute n'est délivrée) ; (2) FSIN/FCOS/FSINCOS/FPTAN de ±inf : IE et l'indéfini (`c000000000000000:ffff`), FSINCOS/FPTAN le poussent deux fois, C2 = 0 — seul un |x| ≥ 2^63 *fini* prend le chemin C2 (ST inchangé, pas de push) ; (3) opérandes NaN, pour toutes les transcendantes, FSCALE et FSQRT : un SNaN lève IE et est rendu silencieux (signe et charge utile conservés), un QNaN se propage tel quel sans IE, avec deux NaN c'est celui de plus grande mantisse qui gagne (le positif à égalité), la règle NaN prime sur le domaine ; (4) un NaN produit par des opérandes non NaN (0·log2 0, 0·log2 ∞, ∞·log2 1, log2 x<0, 0·2^∞, ∞·2^-∞, 0·log2(1+∞), √(x<0)) est un « opérande arithmétique invalide » : IE et l'indéfini ; FYL2X(0, y fini ≠ 0) lève ZE (pas avec y = ±∞) ; (5) F2XM1 hors [-1, 1] : ST(0) inchangé pour tout |x| > 1 fini sur ce CPU (mesuré pour 1,5, -1,5, 3, 10, -70, 1024, 60, ±1e300), ±inf suivant le SDM (+inf, -1) — reproduit ; (6) FSCALE dans les dénormalisés : un seul arrondi dans l'interpréteur comme dans le noyau (1,25·2^-74 par 2^-1001 → 2^-1074, plus 0). Au passage FLD/FSTP m80, FSAVE/FXSAVE conservent signe et charge utile des NaN. Vérification : `verify_trans` (1 500 cas, 0 écart sur les deux exécuteurs) compare désormais les motifs de NaN bit à bit (`nanbits`), IE|ZE|ES du mot d'état (`fpuex`) et FNSTSW & 0x85 / 0x80ff dans EAX ; `verify_trans_known` ne garde que les écarts restants : C0/C3 conservés par le matériel (l'émulateur les efface), PE/DE/OE/UE non modélisés, FYL2XP1 pour x ≤ -1 (ST(0) rendu tel quel par ce CPU). Coût : une comparaison `res != res` par instruction sur le chemin chaud (bench `trans` inchangé).

## D035 — 2026-09-23 — Texte GDI : moteur de polices du navigateur, métriques GDI, polices de l'application
La police bitmap 5×7 intégrée (échelle entière) rendait tout le texte du jeu pixelisé et monospace : le jeu dessine ses textes avec GDI (`CreateFontA`, `GetTextMetricsA`, `GetTextExtentPoint32W`, `ExtTextOutW`) dans une section DIB qu'il envoie ensuite en texture, avec ses propres polices (extraites en fichiers temporaires puis `AddFontResourceExA`, introuvable jusqu'ici). Choix : un *moteur de texte* (`gfx/gdi/text.js`) qui **réalise** un LOGFONT en taille d'em, métriques TEXTMETRIC (ascent/descent issus des métriques Windows de la police — `usWinAscent/usWinDescent` lus dans l'en-tête TrueType pour les polices de l'application, `gfx/gdi/ttf.js` ; boîte de police du navigateur sinon), interlignages interne/externe, largeur moyenne (pondération OS/2), avances entières par caractère, et **rastérise** avec le moteur de polices du navigateur (Canvas2D d'un `OffscreenCanvas` dans le worker, glyphes placés aux positions entières de GDI, crénage désactivé, couverture 8 bits fondue dans la surface du DC comme le lissage en niveaux de gris de GDI, seuil à 50 % pour `NONANTIALIASED_QUALITY`). Les polices enregistrées par l'application passent par `FontFace` (le thread appelant est garé jusqu'à ce qu'elles soient utilisables : le texte mesuré juste après les utilise) ; les polices système Windows sont remplacées par des familles CSS métriquement proches. Sans canvas (Node : tests, CLI) le moteur garde la police bitmap à l'identique. Couvre TextOut/ExtTextOut (lpDx, ETO_OPAQUE/CLIPPED, alignements, TA_UPDATECP), extents, largeurs/ABC, GetGlyphOutline (métriques et bitmaps 1/2/4/8 bits), énumération, DrawText (retour à la ligne, préfixes, tabulations, DT_CALCRECT). Écart assumé : pas d'hinting TrueType de GDI (métriques à ±1 px de Windows).

## D036 — 2026-09-23 — Conformité CPU sur le corpus d'instructions réellement exécutées
Les suites aléatoires ne couvrent que les formes qu'on a pensé à générer. Le worker peut désormais extraire des régions traduites toutes les **formes d'instructions distinctes** (mnémonique, types et tailles d'opérandes, forme d'adressage, préfixes) avec jusqu'à quatre encodages réels chacune (`tools/headless.mjs --corpus`) ; la suite `corpus` du générateur rejoue chaque encodage tel quel sur l'oracle natif avec des états aléatoires, en relogeant les opérandes mémoire dans la zone scratch par le choix des registres de base/index (ESP maintenu haut pour le cadre de signal d'une faute native, opérandes 128 bits alignés, décalages de chaîne de bits bornés). Exclus : flux de contrôle, instructions système/segment, FPREM partiel et approximations RCP/RSQRT (bits de poids faible propres au modèle). Premier passage sur le jeu (762 formes, 7 134 cas) : trois bugs x87 du JIT (arrondis dirigés en précision 24 bits, FST m32 dirigé dans la plage dénormale du float) et deux de l'interpréteur (FST m32 vers zéro qui perdait le signe, FPTAN/FSINCOS sur pile pleine). Le fichier de corpus reste dans `build/` (dérivé du binaire du jeu, non versionné) ; `make gen` produit la suite quand il existe.

## D037 — 2026-09-23 — Arrondi x87 exact dans le JIT (noyaux arith24 / f32rc)
Le JIT arrondissait les résultats en précision 24 bits en ré-arrondissant le résultat f64 (déjà arrondi au plus près) : faux quand ce résultat tombe exactement sur la grille 24 bits sous arrondi dirigé, ou exactement sur un milieu en arrondi au plus près (double arrondi) ; et FST m32 sous arrondi dirigé ignorait la plage dénormale et le dépassement du float. Deux noyaux WebAssembly purs du module runtime (`fpmath-round.js`, importés comme les transcendantes, D033) reproduisent exactement l'interpréteur : `arith24(a, b, op, rc)` refait l'opération avec son terme d'erreur exact (TwoSum, TwoProduct de Dekker, restes exacts de la division et de la racine) puis arrondit la mantisse à 24 bits selon RC et le signe de l'erreur ; `f32rc(x, rc)` écrit le float de FST m32 (pas de 2^-149 dans les dénormaux, signe conservé vers zéro, infini ou plus grand float au dépassement selon RC). Le chemin chaud reste en ligne (au plus près, plage normale, hors milieu exact : `f32.demote`/`f64.promote`) ; le test de milieu ajouté ne coûte rien de mesurable (micro-bench x87 PC=24 : 29,0 → 24,7 ns/itération). Les deux tests `todo` de double arrondi deviennent résolubles.
